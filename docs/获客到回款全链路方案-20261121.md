# 获客 → 邀约 → 到店谈案 → 签约回款：全链路数字化方案

> 2026-11-21 · 业主新增目标
> 现状：**获客前段（线索/邀约/谈案）此前完全没有数据模型**，`Intake` 是「已决定接案之后」的登记。
> 本方案先给完整路线图，阶段一已交付可运行成果（见 §六）。

---

## 一、为什么这一段必须单独建模

系统原有的起点是 `Intake`（收案登记）：登记后要走冲突检索与审批。但真实业务里，
大量线索是「问一句就走」「还在比价」「没决定要不要委托」。

把它塞进 `Intake` 会有两个后果：

1. **收案列表被噪声污染**——律师要在 20 条「问过价没下文」里找真正要办的案子；
2. **算不出转化率**——而转化率是获客唯一要回答的问题。

所以线索独立成 `Lead`，与 `Intake` 分开，转化时才建立关联。

---

## 二、数据模型（阶段一已落地）

```
Lead（线索）
  name / phone / wechat / organization
  source: REFERRAL | ONLINE | OFFLINE | PARTNER | AD | OTHER
  sourceDetail            # 谁介绍的、哪个平台、哪场活动
  stage: LEAD → INVITED → VISITED → CONSULTED → CONVERTED
                                             ↘ LOST（必填原因）
  category                # 意向业务类别（与 MatterCategory 同枚举，便于按类别算转化率）
  expectedAmount          # 预计标的/收费（获客看板用，不进财务）
  ownerId                 # 跟进人
  invitedAt / visitedAt / consultedAt   # 三段各自的时间戳（漏斗分析用）
  convertedIntakeId @unique             # 转化后的收案（唯一，防重复转化）
  lostReason / lostAt

LeadActivity（跟进时间线）
  type: CONTACT | INVITE | VISIT | CONSULT | NOTE
  happenedAt / channel / note / createdById
```

**为什么三类动作要落时间线而不是只改字段**：字段只保留最后一次，而获客要看
「第几次联系才约到」「从邀约到到店隔了几天」。没有时间线，这些问题答不了。

---

## 三、状态机与一条铁律

```
LEAD ──联系──> (阶段不变)
LEAD ──邀约──> INVITED ──到店──> VISITED ──谈案──> CONSULTED ──转收案──> CONVERTED
   └────────────── 任意阶段 ──流失──> LOST（必填原因）
```

**铁律：转化只能从 `CONSULTED` 发起。**

不提供「线索直接转收案」的入口。理由：
如果允许跳过，那么「到店」「谈案」两段会被系统默认跳过（人总是走最短路），
漏斗数据永远漂亮但不可信——而这条链路存在的全部意义就是让漏斗可信。

**阶段只向前推进**：补录更早阶段的动作（例如已到店后补记「上周就约过」）
不会把阶段拉回去。补录是常态，回退会让漏斗统计倒挂。

---

## 四、签约与回款（复用现有，不新建）

这一段**不需要新模型**——系统已有完整实现：

| 环节 | 现有实现 | 是否够用 |
|---|---|---|
| 签约 | `Intake` → 冲突检索 → `convertIntakeToMatter` → `Billing`（委托合同/补充协议） | 够 |
| 收费安排 | `Billing`（一案一签，合同额，补充协议） | 够 |
| 回款 | `FeeEntry`（两步确认，财务岗确认） → `Payment` → `Allocation` 核销 | 够 |
| 开票 | `InvoiceRequest` → 审批 → 开具 → 与实收勾稽 | 够 |

转化时线索把 `name`/`phone`/`organization`/`category` 带进 `Intake`，
避免律师在收案向导里重录——**但不替代**冲突检索与收案审批，那条链照原样走。

## 五、漏斗指标（阶段二做看板）

| 指标 | 定义 | 为什么是它 |
|---|---|---|
| 线索量 | 期间内新增 Lead 数 | 分母 |
| 邀约率 | 有 INVITE 动作的线索 / 线索量 | 判断「有没有人跟」 |
| 到店率 | 到 VISITED 及以后 / 已邀约 | 判断邀约质量（约了不来最说明问题） |
| 谈案转化率 | CONVERTED / 到过 CONSULTED | 判断报价与谈案能力 |
| 整体转化率 | CONVERTED / 线索量 | 唯一可对外比较的数 |
| 获客成本 | 渠道投入 / 转化数 | **阶段三**，需渠道费用登记 |
| 平均转化天数 | convertedAt − createdAt 中位数 | 判断成交周期 |

**口径必须固定**：转化率的分母是「期间内新增的线索」，不是「期间内转化的线索」
（后者会把跨期成交算进来，导致比率可以超过 100%，是常见的自欺）。

## 六、阶段划分与当前状态

| 阶段 | 内容 | 状态 |
|---|---|---|
| **一** | 线索登记 / 邀约 / 到店 / 谈案 / 流失 / 转收案 + 跟进时间线 + `/leads` 页面 | ✅ **已完成**（本批） |
| 二 | 获客看板（漏斗 + 转化天数 + 负责人对比） | ⏳ 下一批 |
| 三 | 渠道费用登记与获客成本（ROI） | ⏳ 需要真实渠道数据才有意义 |
| 四 | 官网/公众号表单接入（自动进线索） | ⏳ 需要外部对接与密钥 |
| 五 | 邀约提醒（约了时间没到店要提醒）| ⏳ 可复用 `ReminderDelivery` 台账 |

**阶段一验收判据（已实测）**：
- 电话与微信都空 → 拒绝登记（后面无法邀约）
- INVITE/VISIT/CONSULT 逐段推进并落时间戳
- 补录更早阶段动作不拉回阶段
- 未到 CONSULTED 不能转收案
- 转化成功后 `Intake` 建出、线索 `CONVERTED`、回填 `convertedIntakeId`、不能转两次
- 流失必须写原因，流失后不再记跟进

## 七、风险与取舍

| 风险 | 处置 |
|---|---|
| 律师嫌麻烦不记线索，链路空转 | 只强制姓名 + 电话/微信其一；跟进只需一次点击（按钮已按阶段变化，不需要选类型） |
| 线索与客户重复录入 | 阶段二做「线索转客户时回填」；当前线索只带联系方式，不建 `Client` |
| 转化率被美化（跳过到店谈案） | **代码级拦截**：只能从 CONSULTED 转（见 §三铁律） |
| 流失原因被随手填「其他」 | 用 `promptDialog` 必填 + 提示示例；阶段二统计「其他」占比作为数据质量指标 |
| 线索跨期成交拉高比率 | 分母固定为「期间新增」（见 §五口径） |

**明确的取舍：阶段三/四是本方案里最不值钱的部分。**
渠道费用与表单接入都需要真实外部数据与密钥；3–30 人律所的获客主要靠转介绍，
做出来大概率是空表。**先把阶段一/二用满一个月，再决定要不要做三四。**
