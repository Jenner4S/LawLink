# 运行时健康巡检（2026-11-22）

> 目的：确认系统在真实运行下没有隐藏的报错噪音与无界增长。
> 依据：`docker logs lawlink-app`（近 2000 行）、数据库状态表、cron 启动痕迹。

## 一、应用日志（近 2000 行）

| 错误类型 | 次数 | 判定 |
|---|---|---|
| `Failed to find Server Action "..."` | **251** | **噪音，非缺陷**：部署换版后，浏览器里仍开着的旧页面按旧 action id 提交。用户刷新即消失。 |
| `ActionError: 只能回应派给自己的线索` | **8** | **预期行为**：来自验收金线第③步「非本人接单」，恰证明服务端拦截生效 |
| ECONNREFUSED / Prisma 错误 / Unhandled | **0** | — |

**结论**：没有隐藏的异常。第一类 251 次全部由「换版后旧页面」造成，
换版频繁的调试期属正常；真实用户只会遇到一次「点一下没反应」，刷新即可。

`src/instrumentation.ts` → `registerCronJobs()` 已注册，容器日志可见每 2 分钟触发：


- `reminder_delivery` 15 行**全为 PENDING、无 lastError** —— 因为提醒按 `dueAt` 到点才发，
  未到期不投递是正确行为，不是积压失败。
- 失败类审计全库只有 `LOGIN_FAILED`（10 次，登录失败记录），**无任何 *_FAILED_CRON**。

> **一次自我纠正**：我最初 grep 调用方时只看到测试引用 `deliverPendingReminders`，
> 一度判断「生产没接线」。实际 `scheduler.ts` 里就有 `deliverPendingReminders(20)`，
> 是我把 grep 输出截断了。**结论必须以完整证据为准，不能凭一次搜索下判断。**

## 三、发现并修复的真实风险：外部调用台账无界增长

| 项 | 事实 |
|---|---|
| 表 | `ExternalCallLog`（服务名、耗时、是否成功；**不含正文与凭据**） |
| 行数 | **28148**，全部集中在 2026-11-18 ~ 11-20（测试回放） |
| 清理策略 | **无**（原状：无 `deleteMany`、无 TTL、无 cron） |
| 后果 | 统计查询（`getExternalCallStats` 的 groupBy）随行数线性变慢；库盘持续增长 |

**处置**：新增保留期机制，而不是简单删除。

- `src/server/settings/retention.ts`：
  `getExternalCallLogRetentionDays` / `saveExternalCallLogRetentionDays` / `purgeExternalCallLogs`
- 默认**保留 365 天**：跨年度审计通常回看一年；该表只有调用元数据，留存风险低；
  低于 90 天会损害「三个月前那次批量失败是什么原因」这类排查
- **设为 0 = 不清理**（有的所要求全量留存取证数据）
- 只删 `createdAt < cutoff`，**永不触碰当期**；分批 5000 行，避免长事务锁表
- 每轮删除写审计 `CALL_LOG_PURGED`（含保留天数、截止时间、删除条数）——删了什么要能查
- cron：每周日 03:30（避开既有作业），失败走 `EXTERNAL_CALL_LOG_RETENTION_FAILED_CRON`

**测试**：6 例（默认 365、坏配置回落、只删超期、0=不清理、保留期可配、分批删干净），
**三次变异各自变红**（去掉时间过滤 / 忽略 0 / 只删一批）。

## 四、未做与边界（如实）

- **慢查询未做量化**：本库未启用 `pg_stat_statements`，无法给出 P95。
  替代观察：现有统计表 `ExternalCallLog` 走 `createdAt` 与 `(service, createdAt)` 索引，
  清理上线后行数不再单调增长。若后续接入真实流量，建议启用该扩展再测。
- **多实例部署**：cron 是进程内的，多副本会重复触发。投递器已有进程内防重入标志，
  但**跨进程仍需数据库级租约**（需迁移，属红线，见既有审计文档）。
  当前单实例部署下成立，已在 `delivery.ts` 注释中标注。
- 251 次旧 Action 报错不修：它是 Next.js 的部署语义，不是本项目可配置项。
