## 一、源码交付：**不该卖 15–25 万，这个档位本身要重构**

### 1.1 先确认一个硬事实

```
gh repo view lawflow-boop/LawLink  →  {"private": false, "visibility": "PUBLIC", "lic": "mit"}
gh repo view Jenner4S/LawLink      →  {"private": false, "visibility": "PUBLIC"}
LICENSE → MIT License
```

**两个仓库都是公开的，协议是 MIT。**

MIT 的含义：任何人可以免费克隆、使用、修改、再分发，唯一义务是保留版权声明。

### 1.2 所以「源码交付」卖的是什么？

| 你以为在卖 | 实际上 |
|---|---|
| ❌ 访问源码的权利 | **GitHub 上免费，任何人都能克隆** |
| ❌ 源码的所有权 | MIT 已授权给全世界 |
| ❌ 二次开发的许可 | MIT 本来就允许 |

**结论：15–25 万「源码交付」在国内客户做过一次搜索后就会被质疑。**
销售拿着这一档去见懂技术的客户，第一句话就会被问倒：「你们 GitHub 不是公开的吗？」

### 1.3 与德尔普不可比

德尔普源码版 14.1 万是**闭源产品**卖源码——客户不付钱永远拿不到。
我们的源码是免费的，两者**不是同一个商品**。

### 1.4 建议：取消「源码交付」，换成「企业支持包」

| 项 | 内容 | 定价依据 | 建议价 |
|---|---|---|---|
| **私有化部署** | 安装、配置、数据迁移、管理员培训 | 产品交付 | **12–18 万** |
| **定制开发余额** | 预付 20 人日，按客户需求改（这是唯一合法的人日用法） | 人日 × 2800 | **5–6 万** |
| **年度技术支持** | 8×5 响应、季度服务报告、升级协助 | 服务订阅 | **3–6 万/年** |
| **合计首年** | | | **20–30 万** |

**这套结构的好处**：

1. **每一分钱都有对应交付物**——不会出现「我付了 15 万买了一堆 GitHub 上免费的东西」
2. **定制开发用余额制**，客户可控，你也有人日收入的正当理由
3. **年度支持是持续收入**，且与「先建 SLA 再收订阅」的路径一致

**如果客户坚持要「源码」**，正确回答是：

> 「源码是 MIT 开源的，您可以直接从 GitHub 获取，不需要付费。我们收的是**部署、定制和长期支持**。如果您要的是『有人对这套代码负责』，那是我们的年度支持服务。」

## 二、销售端不能接受「P11/P13/P14 不报」——四个解法

### 2.1 先纠正一个前提：**「不报」≠「不谈」**

销售可以谈，只是**不能承诺交付**。区别在于：

| ❌ 不能做 | ✅ 可以做 |
|---|---|
| 报一个价，签合同，交不出来 | 告诉客户「现在没有，X 时点会有」或「这样做可以满足」 |
| 把 P11 改个名字硬卖 | 卖 P05 + 门户升级权 |
| 承诺「下个月就能做」 | 承诺「按里程碑，达成后通知」 |

**把「不可报清单」改名为「不可即时交付清单」**——销售的心理阻力会小很多。

### 2.2 解法 A · P11 客户门户版 → 预订锁价 + 分期交付

**现状**：D12 门户 0%，但**架构方案已完成**（[客户门户架构方案](./客户门户架构方案-20261120.md)，含 5 个架构决策、6 张表、S1–S3 分期）。

**可承诺的**：
```
签约 P05（10–14 万）
  + 门户升级权定金（2–3 万，可抵将来价款）
  + 门户按 S1–S3 交付（预排 7 周：身份 2 周 + 只读视图 3 周 + 工单 2 周）
```

**话术**：
> 「客户门户我们已经在建，架构方案已经定稿。现在签约的话，门户可以作为升级项——
> 您先付定金锁住当前价格，门户上线后补差交付。如果您等门户做完再签，那时价格会调整。」

**⚠️ 必须写进合同的约束**：
- **不写死交付日期**，写「按季度里程碑推进，每个里程碑达成后书面通知」
- 定金条款写明「因技术原因未达成时全额退还」
- 不要在合同里写「门户含 X 项功能」的清单（D12 五项还没实现）

### 2.3 解法 B · P13 集团多分所版 → 多实例 + 集团汇总

**现状**：AGENTS 明确「不做共享 SaaS 多租户，一个律所一套实例」。**多租户架构确实不做**。

**但有一个能成立的替代**：

```
各分所各部署一套独立实例（数据各自独立，互不可见）
  ↓
集团层面通过 API 拉数汇总
  /api/reports/export   /api/finance/export  （都存在）
  ↓
集团 BI / Excel 看合并报表
```

**能交付的**：多实例部署 + API 汇总对接 + 集团报表模板
**不能交付的**：单点登录跨所、实时合并账、跨所案件调阅

**话术**：
> 「我们不做多租户，这是刻意的——律所数据本来就该各所独立。集团层面我们用
> **多实例 + API 汇总**：各所独立部署，集团通过接口拉取合并报表。
> 好处是任一分的所数据泄露不会波及其他所。跨所实时调阅案件这个做不到，需要您确认能接受。」

**定价**：每所按标准档（12–18 万）+ 集团汇总对接实施（3–5 万）+ 每所年支持

#### ✅ 已实测（2026-11-20）

建两个独立临时库（模拟 A 所 / B 所），各灌案件后分别跑 `getReportData`，验证结果：

| 实例 | newIntake | inProgress | byCategory(CIVIL_COMMERCIAL) | byLawyer |
|---|---|---|---|---|
| A 所 | 3 | 3 | 3 | 律师A |
| B 所 | 5 | 5 | 5 | 律师B |
| **合并** | **8** | **8** | **8** | 2 人 |

**结论：数据层可行**——两实例独立产出结构化 `ReportData`，按维度求和即可。
`getReportData` 返回的是 JSON 结构（`kpis` / `byCategory` / `byLawyer` / `byClientReceivable` / `byClientSource`），不是 xlsx 二进制。

#### 实测暴露的两个前提（必须写进合同）

| 发现 | 影响 | 处置 |
|---|---|---|
| **`userId` 跨实例不通用** | 合并必须按**姓名**聚合，不能按 id | 合同写明「集团报表按律师姓名合并，**同名律师会合并为一行**，需各所命名不重复」 |
> 补 JSON 端点后，集团汇总就是「N 个 HTTP 请求 + 按维度求和」，
> 客户用 Excel / BI / 一段脚本都能做，不依赖我们。

#### ✅ `?format=json` 已实现并端到端验证（2026-11-20）

**实现**：`src/app/api/reports/export/route.ts` 增加 `format=json`（默认仍是 xlsx，行为不变）。
返回结构：`schemaVersion / periodKey / periodLabel / start / end / generatedAt / mergeGuide / data`。

**`mergeGuide` 是接口契约，不是注释**——它用字段名明确告诉消费方：

| 类别 | 内容 |
|---|---|
| `summable`（13 项） | 直接相加的字段 |
| `derived`（1 项） | `kpis.archiveRate` —— **必须用 Σarchived ÷ Σclosed 重算，不可相加** |
| `instanceLocalKeys`（2 项） | `userId` / `clientId` 是实例本地主键，**须按名称合并** |
| `booleanAnd` | `financeReady` 任一 false 则集团 false |
| `groupBy` | 四个明细列表各自的分组键 |

**端到端实测（两个真实应用实例，真 HTTP）**：

```
起第二个应用容器（同一镜像 4b14c246a4ad，端口 3001，指向克隆库）
  ↓ 各自登录、各自取 JSON
3000 → newIntake 7 / inProgress 7 / 律师 7 人
3001 → newIntake 7 / inProgress 7 / 律师 7 人
  ↓ 按 mergeGuide 合并
合并 → newIntake 14 / inProgress 14 / 律师 7 人（同名合并）/ archiveRate 重算未相加 ✅
```

**实测暴露的既有行为（非本次引入）**：未登录访问返回 **307 跳登录页**，
不是 401——原因是 `src/proxy.ts`（Next.js 16 的 middleware 新约定）把
`/api/reports/export` 纳入保护范围，在进入路由前就重定向。
**集团汇总方需先建立会话并保持 cookie**；拿不到 401 不代表接口异常。

**清理**：第二容器已移除、克隆库已 DROP、零残留。

### 2.4 解法 C · P14 涉外大客户版 → 拆分，卖能卖的部分

**现状**：LEDES 0%、信托 0%、多语言 0%。

**逐个拆**：

| 客户诉求 | 能不能满足 | 怎么做 |
|---|---|---|
| 涉外案件办案管理 | ✅ 能 | 正常用 P04/P05，程序类型支持非诉/仲裁 |
| **LEDES 账单** | 🟡 半能 | LEDES 是**格式**，不是系统能力。可写一个导出转换脚本，把人天/费率导出成 LEDES 1998B 格式。**这是定制开发，按人日报价（约 8–12 人日）** |
| **信托 / IOLTA 账户** | ❌ 不能 | 中国大陆律所不适用该制度。**如实说，不要硬凑** |
| 多语言界面 | ❌ 不能 | 目标客户全中文 |
| SSO | ✅ 能 | OIDC 已实现 |

**话术**：
> 「信托账户是普通法体系的概念，中国大陆律所不使用，我们不做这块。
> LEDES 是账单格式，我们可以做一个导出转换，按定制开发计价。
> 办案本身我们支持得很好，涉外案件的程序管理没有问题。」

**这条是唯一可以「卖一部分」的方案**——因为它拆开后有些诉求是能独立满足的。

### 2.5 解法 D · 转介（兜底）

客户就是要**真正的多租户集团版**或**信托账户**——那就不适合我们。

**话术**：
> 「这块不是我们的方向。如果这是您的核心需求，我建议您看 XXX（同行的集团版）。
> 我们可以做的是各所独立部署 + 集团报表汇总，您比较一下哪个更符合。」

**转介不是丢单，是维护信任**。一个明知做不了还硬签的客户，会在交付期变成最大的麻烦。

> 我们收的是部署、定制和长期支持。

## 六、本文的不确定性

1. **「多实例 + API 汇总」已用两个真实应用实例端到端验证**（案件计数、律师维度、比率重算）。
   但**未用真实财务数据验证金额维度**——`byClientReceivable` / `byClientSource` 的
   Decimal 序列化与跨实例客户同名合并尚未实测，对客户承诺财务汇总前需补测。
2. **LEGES 导出人日（8–12）是估算**，未做技术验证。
3. **预订锁价的定金比例（2–3 万）**是建议值，需结合你的现金流偏好调整。
4. **P14 拆分卖的可行性**取决于客户是否接受「办案用我们、账单另配」——这是商务判断，不是技术判断。
