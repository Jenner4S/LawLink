## 八、本轮新增的三个"尺子"（2026-11-23 后补）

这三个都是**给以后的人用的**，不是给现在用的。写在这里以免它们散落在台账里被忘掉。

### 1. 时区口径守卫 `scripts/audit-timezone.mjs`（已进门禁，第 12 步）

容器跑 **UTC**、业务口径是**上海**。已出过一次真事故：线索月界按本地字段算，
「上海本月 00:00 登记的线索」被判成上月 → 质量环比全 null、投放成本月份错一月、
`getLeadToCash` 与漏斗口径分叉。

守卫会静态扫 `src/` 里对本地日历字段的用法，**未登记即发布失败**；
每条白名单必须写"为什么这里不用改"。
新增代码时若用了 `getFullYear/getMonth/getDate`，会立刻被指出来。

口径约定（容易搞混，记在这里）：
- **date-only**（期限、保全起止日）→ 上海日子 + **正午载体**（`civilFromKey(shDayKey())`）
- **now 相关**（今天/本月/按小时）→ `shStartOfDay` / `shMonthStart`
- **展示** → `formatDate` / `formatDateTime`（已固定 `Asia/Shanghai`）

### 2. 取数基线 `scripts/bench-leads.mjs`

`/leads` 背 13 个并行取数。这个脚本给出一把可复现的尺子（热身 3 次 + 采样 5 次取中位），
并写明一条教训：**别拿第一次的数字当基线**——我第一版每项只跑一次，
首项显示 45.3ms，实际那是冷启动，热身后同一查询 2.2ms。

### 3. 漏斗量级告警（`getLeadFunnel`）

5 万行压测（临时库实测）：`getLeadFunnel` **272ms**（1.75 万行）、
SQL 聚合版 **24.7ms**（约 11 倍），但**没改**——`activities` 承载邀约/到店/谈案口径、
改 SQL 会动中位数语义（属业主口径决策）。

替代方案：超过 1 万行时打一条 warn，文案带实测数与文档链接。
不做自动降级——降级会让"数字悄悄变少"，比慢更糟。
