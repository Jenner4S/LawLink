# 测试分层与快跑清单

> 2026-11-22 · 依据 `scripts/test-layers.mjs` 的实际输出（事实，非估计）

## 一、为什么要分层

186 个测试文件里有一部分是**真库测试**：每个都要建临时库、跑 `prisma migrate deploy`、
结束后 `DROP DATABASE ... WITH (FORCE)`。全量跑十几分钟。

改一个纯函数（比如金额四舍五入）也要等全量，结果是人开始**跳过测试**——
那比没有测试更危险。

分层之后的用法：

| 场景 | 命令 |
|---|---|
| 只改纯逻辑 | 按 `--unit` 清单挑文件跑，或 `npx vitest run src/tests/lib` |
| 改了数据访问 / 事务 / 迁移 | 按 `--db` 清单跑 |
| 交付前 | `npx vitest run` 全量 + 各门禁脚本 |

## 三、分类判据（宁可保守）

出现下列任一特征 → 归为**真库**：

- `createTempDatabase`（本项目脚手架）
- 直接 `CREATE DATABASE` / `DROP DATABASE`
- 设置 `process.env.DATABASE_URL`（模块级单例在 import 期就要连库）
- `new PrismaClient` / `datasourceUrl`
- `prisma.<model>.<findMany|create|update|upsert|…>`
- `prisma.$transaction` / `prisma.$queryRaw`

**取舍**：误判成单元的代价是「以为能快跑，其实连不上库直接红」，更误导人；
误判成真库的代价只是「多花几分钟」。所以判据偏保守。

**踩过的坑**：第一版用裸方法名 `.update(` / `.create({` 做判据，
把 `createHash(...).update(...)` 判成了真库（`crypto.test.ts` / `desktop-checkout.test.ts`）。
改成锚定 `prisma.xxx.method(` 后消除。

## 四、真库测试为什么必须有

真库测试不是"更严谨的单元测试"，它验的是**只能真库验的东西**：

| 能力 | 只能真库验的原因 |
|---|---|
| 唯一约束 / 外键 / 级联删除 | mock 掉 SQL 就等于断言"我调用了某个函数" |
| 事务回滚与隔离 | 需要真实并发与提交语义 |
| 迁移是否与 schema 一致 | 需要 `migrate deploy` 后的真实结构 |
| 金额口径（核销、坏账、风代） | 需要真实的 Decimal 与聚合行为 |
| 触发器（审计不可删等） | 数据库层实现，应用层测不到 |

所以这里的策略不是「减少真库测试」，而是**让不需要真库的测试别连库**。

## 五、维护

新增测试文件后跑一次 `node scripts/test-layers.mjs` 即可看到分布变化。
若真库占比继续升高，优先检查新测试是否真的需要库——
很多"看起来要库"的用例其实只需要一个纯函数。

## 六、员工侧金线的有效性（2026-11-22 已实测）

`scripts/golden-thread-write.mjs` 的「界面提交后真实落库」这条断言，
此前只通过门户侧证明过机制。本轮做了**独立变异验证**：

1. 在 `createClient` 注入环境变量开关（`MUTATION_SKIP_WRITE=1` 时跳过写入）；
2. 用该开关单独构建并起一个变异实例（端口 3100）；
3. 以 `BASE=http://localhost:3100` 跑金线 → **结果 8 通过 / 1 失败**，
   失败正是「客户真实落库」，诊断显示 `errs:["客户已创建"]` 但库里没有行；
4. 恢复源码、停实例、清构建产物，探针残留 = 0。

结论：**这条断言不是空转**，能捕捉"界面点了但没写库"。

### 固化为脚本（2026-11-22）

手工流程已抽成 `scripts/mutation-golden.mjs`，一条命令完成：
注入变异 → 构建 → **立刻恢复源码**（产物已固化变异）→ 起实例 → 跑金线 →
判定 → 停实例/清产物/还原被 `next build` 改写的生成文件。

```bash
node scripts/mutation-golden.mjs --dry                 # 只查锚点是否还命中
node scripts/mutation-golden.mjs --only client-skip-write
```

**判定严格**：必须「退出码非 0」**且**「输出含预期那条检查」才算有效。
只有非 0 不算——服务没起来、CDP 掉了都会非 0，那是假阳性。

**两个陷阱（都踩过，写进脚本注释）**：

1. **早返回会让 TS 类型收窄失效**：在 `create` 前插 `return` 会触发
   `'viewer' is possibly 'null'`，可用 `as never` 绕过（`client-skip-write` 就是这么做的）；
2. **`if (false)` 死分支同样破坏收窄**，不要用它"注释掉"写入。

若变异让 `next build` 失败，脚本会明确报告「**变异本身不合法，无效——不算金线通过**」，
而不是把它当成"金线抓住了缺陷"。

**注意成本**：每个变异跑一次 `next build`（约 8 分钟）。这是按需工具，
改动写入路径时跑一次即可，不放进每次 CI。

## 七、发布门槛（2026-11-22 新增）

门禁脚本已有 8 个，但「发版前该跑哪几个」靠人记 ——
结果是同一份代码在不同轮次给出的证据不一样。`scripts/release-check.sh` 把顺序固定：

```bash
./scripts/release-check.sh            # 全量（测试/界面/金线/构建）
./scripts/release-check.sh --fast     # 只跑静态检查（提交前用，约 30 秒）
./scripts/release-check.sh --no-build # 全量但跳过构建
./scripts/release-check.sh --deploy   # 全量通过后再部署（需显式开启）
```

**顺序有讲究**：快速静态检查（秒级）→ 测试（十几分钟）→ 界面 → 变异探针 →
真机金线 → 构建。**便宜的先跑**：错在类型或规范上，不该等跑完 15 分钟测试才发现。

**任一步失败即中止后续**（含部署）；每次都产出一份证据摘要：

- `outputs/release-check/<时间戳>.md`（可贴进交付记录）
- `outputs/release-check/<时间戳>.log`（完整输出）

摘要含提交号、时间、每步结果与关键数字（TS 错误数 / 测试数 / UI 项数 /
探针数 / 金线通过数），**不必再手抄**。

### 一个环境坑（记下来）

macOS 自带 bash 3.2 在 `set -u` 下，`$STAMP）`（变量后紧跟中文全角括号）
会把括号首字节吞进变量名，报 `STAMP?: unbound variable`。
写法统一成 `${STAMP}` 即可。

## 并发用例的超时保护（2026-11-23）

### 事实

门禁一度变红，但日志显示的是「文档 1883 / 实际 ?（未测成）」——
看起来像文档写错，实际是 **vitest 里有一个用例超时**，导致读不到测试数。

真凶：`login-lockout.test.ts` 的「并发 8 次失败：计数恰好 +8」。
单跑 0.3s，**全量并行跑**（199 个测试文件同打一个库）时超过默认 5s。

### 处置

对 **10 个并发写库用例**统一加 30s 超时（`vi.setConfig({ testTimeout: 30_000 })`
或单个 `it(..., 30_000)`）：

`login-lockout` / `client-contacts-race` / `preservation-renew-race` /
`finance-ledger-correction` / `portal-s1` / `archive-borrow-race` /
`business-chain-e2e` / `finance-ledger-sign` / `sms-generate-race` /
`writeoff-items` / `reminder-lease-backoff` / `finance-ledger-tx-gaps`

**为什么不降低并发数**：这些用例的价值正是"并发下仍然正确"。
削弱并发等于把原子性回归守卫变成摆设 —— 宁可放宽超时。

### 主动验证：`scripts/stability-check.sh`

```
./scripts/stability-check.sh        # vitest×3 + 金线×2（默认）
./scripts/stability-check.sh 5 3    # vitest×5 + 金线×3
```

连跑并检查探针残留。**局限如实写**：通过 ≠ 没有 flaky，
默认样本只 5 次，只能说明"本次机器状态下未复现"。
