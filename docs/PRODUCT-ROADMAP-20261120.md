## 零、先看清一件事

评估结果：**129 项功能，已实现 45、部分 41、缺失 43，加权 50.8%。**

但**平均数会说谎**。真实形态是两极：

| 主轴（案件 + 合规） | 覆盖 | 副轴（获客 + 经营） | 覆盖 |
|---|---|---|---|
| 利益冲突检索 | 76% | 市场与获客 | 39% |
| 文档与知识 | 63% | 客户价值经营 | 47% |
| 案件与委托 | 66% | 案源管道 | 49% |
| 组织权限与合规 | 66% | 客户门户 | 0% |

**这不是质量问题，是定位问题**：LawLink 从第一行代码起就是「办案系统」，
`CRM` 三个字只在「收案前」这一段成立。要决定的是**补副轴，还是承认它只是办案系统**。

> **本计划的前提假设**：目标是让 P04/P05/P08 三个中端方案可交付（覆盖 60% → 75%+），
> 而不是去追 P03 市场获客（39%）——那等于再造一个产品。
> **如果前提错了，整份计划作废，请直接否掉。**

## 一、分四个阶段

### 阶段 0 · 把已有的变成能用的（1–2 周，最高 ROI）

**不写新功能，只补入口。** 这些能力代码都在，用户点不到：

| 项 | 现状 | 动作 |
|---|---|---|
| 客户合并 | `mergeClients` 已实现，零引用 | 客户列表加「合并到…」 |
| 律所文书更新 / 版本历史 | `updateFirmFile` / `getFirmFileVersionHistory` 零引用 | 文书详情加「编辑」「历史」 |
| 保全 改 / 删 | `updatePreservationCase` / `updateTarget` / `deleteTarget` 零引用 | 保全卡加「编辑」「删除」 |
| 当事人 ↔ 工商绑定 | `bindPartyToEnterprise` 等零引用 | 当事人卡加绑定入口 |
| 任务删除 | `deleteTask` 是死代码（责任面板取代） | **删掉**，不补入口 |

**判据**：可达性审计从 59 条不可达降到 ≤ 25。
**为什么先做这个**：不花设计成本，直接提升 5 个「部分实现」到「已实现」，评估分从 50.8% → 53% 左右。

---

### 阶段 1 · 把 P04 / P05 / P08 推到可交付（6–10 周）

这三个方案现在都是 63–66%，**卡在同一个地方：缺 1–2 个模块**。

| 方案 | 当前 | 卡在哪 | 补齐后 |
|---|---|---|---|
| **P04 客户+案件** | 63% | D01 客户主数据只有 60%：无分级、无生命周期、无关系图谱、无批量导入 | ~78% |
| **P05 交付协同** | 66% | D07 沟通：无关怀计划、无 NPS；D09：无排期冲突检测 | ~78% |
| **P08 合规强化** | 66% | D05 已有 71%，D14 有 78%——**已接近**，只差定期全量复检与个保法删除 | ~85% |

#### 具体要做的事

**1. 客户主数据补全（D01，4 周）**
- 客户分级 A/B/C + 行业 + 规模（枚举与字段，无迁移风险）
- 客户生命周期状态（潜在 / 在谈 / 在服务 / 沉默 / 流失）
- 客户批量导入（复用案件导入的 CSV 通道）
- ⚠️ 客户关系图谱**不做**——它需要独立的实体关系建模，收益与成本不成比例

**2. 沟通与关系（D07，3 周）**
- 「该联系未联系」SLA：按客户分级配置联系间隔，超期进待办
- 常顾到期提醒（90/60/30 天）——同时补上 D13-03
- 会议纪要结构化（现有 Note 的 MEETING 渠道升级为可填决议/承诺字段）
- NPS/CSAT **不做**：需要客户触达通道，而门户是第 3 阶段的事

**3. 日程与期限（D09，2 周）**
- 排期冲突检测（同一律师同一时段两个庭）
- 法院 / 法庭主数据表（现在 courtName 是自由文本，统计做不了）

**4. 合规收尾（D05 + D14，2 周）**
- 定期全量利冲复检（定时任务 + 差量报告）
- 个保法：按留存期自动清理 + 导出证明

---

### 阶段 2 · 打开副轴：客户门户（8–12 周）

**这是最大的单点缺口：D12 五项全零。** 也是唯一能让客户直接感知价值的模块。

| 子项 | 内容 | 为什么必须 |
|---|---|---|
| 门户账号体系 | 独立于员工账号的 Client 身份、单客户隔离 | D12-02，任何门户的前提 |
| 进度 / 文档 / 账单自助 | 客户登录看案件进度、下载已公开文书、查账单 | D12-01 |
| 服务请求工单 | 客户提问 → 内部待办 → 时限 | D12-04 |
| 满意度评价 | 结案后自动邀请 | D12-03 |

**⚠️ 这是一次 Schema 迁移 + 新权限域**，需要独立设计评审。
**做完后**：P11 客户门户版从 54% → ~85%。

---

### 阶段 3 · 获客（不推荐，除非定位改变）

| 模块 | 现状 | 要做的话 |
|---|---|---|
| D03 案源管道 | 49% | 可配置管道 + 看板 + 漏斗分析（约 6 周） |
| D04 市场获客 | 39% | 渠道登记 + ROI + 官网表单接入（约 8 周，且需要真实渠道数据才有意义） |
| D13 客户价值经营 | 47% | 价值评分 + 流失预警 + 年度回顾（约 5 周） |

**我的判断：不要做。** 理由——
- 这三块加起来 19 周，只把 P03 从 39% 推到 ~70%
- 市场获客的数据源在律所外部（官网、公众号、活动），系统内做完了也是空表
- 目标客户（3–30 人律所）的获客主要靠转介绍，不需要管道看板

**如果坚持要做，先做 D13 客户价值经营**（复用现有数据，不需要外部集成），D03/D04 最后。

| 优先级 | 事项 | 周期 | 覆盖提升 | 风险 |
|---|---|---|---|---|
| **P0** | 阶段 0：补可达入口 + 删死代码 | 1–2 周 | 50.8% → 53% | 极低 |
| **P0** | 客户分级 / 生命周期 / 批量导入 | 4 周 | P04 → 78% | 低（加字段） |
| **P1** | 联系 SLA + 常顾到期 + 会议纪要 | 3 周 | P05 → 78% | 低 |

| **不做** | 市场获客、案源管道、移动端、信托账户、LEDES、日历双向同步、电子签、法院平台对接 | — | — | — |

## 三、明确不做的清单（连同理由）

| 项 | 为什么不做 |
|---|---|
| **D11-04 信托 / IOLTA** | 中国大陆律所不适用该制度；做了是照搬普通法概念 |
| **D11-07 LEDES** | 涉外大客户专用，目标客户用不上 |
| **D12-05 多语言** | 目标客户全中文 |
| **D16-05 移动端 App** | 投入产出比差；响应式 Web 已可用（窄屏已验证） |
| **D09-04 日历双向同步** | iCal 单向订阅已覆盖 90% 需求；双向同步是长期维护负担 |
| **D16-04 电子签** | 需对接第三方（e签宝等），涉及费用与合规责任；现有「合同确认留痕」是诚实的降级方案 |
| **D16-10 法院立案平台** | 各地平台接口不统一，且多数不对外开放 |
| **D01-06 客户关系图谱** | 建模成本高，实际使用频率低 |

## 五、本计划自身的不确定性（如实声明）

1. **覆盖度是估算**：逐条判定由我基于代码阅读给出，未逐项跑真实操作验证。误差估计 ±5%。
2. **人日未估**：只给了周数区间，没有拆分。真要做需要按人日细化。
3. **阶段 2 的门户是最大的未知**：它需要新权限域，与现有 RBAC 的关系要单独设计。
4. **前提假设可能错**：如果目标不是「让 P04/P05/P08 可交付」，这份计划的优先级全错。
