# `/leads` 取数性能基线（2026-11-23）

> 这个页面背了 **13 个并行取数**（漏斗、渠道下钻、待上门、积压、投放成本、成本环比、
> 质量环比、列显隐、口径设置、闭环、渠道树、律师清单、线索列表）。
> 持续加功能需要一个可复现的尺子，而不是靠感觉。

## 一、结论（事实）

**当前不是瓶颈，不需要优化。** 热身之后每项 1–3ms，串行合计 **15.4ms**，
而页面是 `Promise.all` 并行 → 墙钟≈最慢一项（3.2ms，不含 React 渲染）。

```
node scripts/bench-leads.mjs

  数据量：Lead=7 Billing=0 Payment=0 ChannelCost=0
  热身 3 次、采样 5 次取中位

     3.2 ms  getLeadToCash(4 次聚合)
     2.5 ms  listLeadChannels + listLawyerOptions
     2.2 ms  listLeads(200 + owner/channel/_count)
     1.7 ms  getChannelQualityComparison(2 期聚合)
     1.4 ms  设置读 2 次(policy/columns)
     1.3 ms  channelCost 列表 + 环比(2 次)
     1.2 ms  getStaleConsultedLeads
     1.0 ms  getUpcomingVisits
     0.9 ms  getLeadFunnel 源查询(本月全量)

  串行合计 15.4 ms；墙钟≈最慢一项
```

## 二、一条重要教训：别拿第一次的数字当基线

我第一版脚本每项**只跑一次**，输出是这样：

```
    45.3 ms  leads.findMany(200 + owner/channel/count)   ← 假的
     7.9 ms  leadToCash(4 次聚合)
     2.8 ms  upcoming 待上门
     ...
```

那 45.3ms 是**首次连接建立 + 查询计划编译**，不是这个查询的成本。热身后同一查询 **2.2ms**。

于是做了一次对照实验（拆开 include 与 _count 单独看）：

```
  2.2 ms  +owner
  2.1 ms  +三者全开
  1.5 ms  裸 findMany(200)
  1.3 ms  +channel
  1.3 ms  +_count.activities
```

**结论**：`include` 与 `_count` 都不是元凶（差 0.7ms 量级）；差异全在冷启动。
脚本因此固定"热身 3 次 + 采样 5 次取中位"。

## 三、随数据量增长时先看哪里（预判，非实测）

| 项 | 风险 | 触发条件 | 改法 |
|---|---|---|---|
| `getLeadFunnel` 源查询 | **中** | 单月线索 > 5 万行时，全量拉取 11 个字段会变慢 | 改 SQL 聚合（`count(*) FILTER`），与质量环比同一写法 |
| `listLeads` | 低 | 已 `take 200` | 需要全量时改分页，而不是放开 take |
| `getChannelQualityComparison` | 低 | 已是单条聚合 × 2 期 | 可合并成一条 `UNION ALL`，但当前 1.7ms 不值得 |
| 其余 | 低 | 单表小结果集 | — |

**不提前优化**：上表第一项在 7 行数据下 0.9ms，改成 SQL 聚合会让
"分母口径"的代码可读性变差（现在的实现能一眼看出哪些线索计入漏斗）。
等真到 5 万行量级再改，届时以本脚本量化前后。

## 四、怎么用

```
node scripts/bench-leads.mjs              # 默认热身 3 / 采样 5 / 慢阈值 50ms
node scripts/bench-leads.mjs --runs 9     # 采样更多，取中位更稳
node scripts/bench-leads.mjs --slow 20    # 想更早看到预警
```

阈值只做**提示**，不作失败退出：性能受机器影响，硬门槛会变成噪声。
本脚本**不进发布门槛**（同理由）。

## 五、未验证的部分（如实写）

- **没有测页面端到端 TTFB**：需要带会话的 HTTP 请求，本脚本只测取数层。
  若将来怀疑渲染或 RSC 序列化是瓶颈，用 `curl -w '%{time_total}'` 带 cookie 另测。
- **没有大数据量实测**：当前库只有 7 条线索，上表"风险"是推断，不是测量。

## 六、5 万行压测（2026-11-23 追加，把 §三 的推断变实测）

临时库造 **50,000 条线索**（单月约 17,513 条），跑同一套基线：

```
  Lead=50000 · 表 11MB

    120.2 ms  getLeadFunnel 源查询(本月全量)  ⚠️
     40.9 ms  listLeads(200 + owner/channel/_count)
     12.6 ms  getChannelQualityComparison(2 期聚合)
      7.6 ms  getLeadToCash(4 次聚合)
      6.9 ms  getStaleConsultedLeads
      2.9 ms  getUpcomingVisits
      1.7 ms  listLeadChannels + listLawyerOptions
      1.7 ms  设置读 2 次
      1.5 ms  channelCost 列表 + 环比
   串行合计 196 ms
```

**§三 的推断成立**：`getLeadFunnel` 是唯一破阈值的一项。

但真跑函数得到更重要的细节 —— **基线脚本低估了它**：

```
getLeadFunnel（含 owner/channel/activities 三个 include）实测：272ms（1.75 万行）
拆开看（1.75 万行）：
    124 ms  裸 select(无 include)     ← 大头：全量拉取本身
    197 ms  +owner                   (+73ms)
    188 ms  +channel(含 parent 嵌套)  (+64ms)
    169 ms  +activities(仅 type)      (+45ms)
    272 ms  全部 include（现实现）
```

### SQL 聚合能到多少（实测）

    4.2 ms  ① 主计数一条 SQL(count FILTER)
    6.8 ms  ② byChannel GROUP BY
    5.3 ms  ③ byOwner GROUP BY
    4.6 ms  ④ bySource GROUP BY
    3.0 ms  ⑤ 转化天数中位数(percentile_cont)
    0.8 ms  ⑥ 流失原因 GROUP BY
    合计 **24.7 ms**

即 **272ms → ~25ms，约 11 倍**。

### 为什么仍然不改（明确取舍）

1. **`activities` 不能删**：漏斗的「邀约/到店/谈案」三个数**不是**按 stage 算的，
   而是按 `LeadActivity.type` 是否有 INVITE/VISIT/CONSULT 算的（见 analytics.ts
   循环体）。删掉这个 include 会直接改口径。
2. **改 SQL 会动中位数语义**：现有实现"偶数取两侧平均"，
   `percentile_cont` 在离散点上行为不同 —— 那是口径改动，应由业主拍板。
3. **真实量级到不了**：一所一年几千条线索，单月 1.75 万行已属异常（多半是批量导入）。

### 于是做了一件低风险的事：量级告警

`getLeadFunnel` 在 `leads.length > 10_000` 时打一条 warn，文案带**实测数据**与
文档链接。真到了这个量级，日志会指路，而不是让人对着 272ms 猜。

阈值定 10,000 的依据：1.75 万行实测 272ms（已值得关注），1 万行按线性估算约 150ms。
不做自动降级：降级会让"数字悄悄变少"，比慢更糟。
