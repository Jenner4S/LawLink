# 数据留存策略（2026-11-22）

> 目的：把「哪些表会无限增长、各自怎么处置」一次说清。
> 上一轮只修了最明显的 `ExternalCallLog`，同类风险值得一次扫清。

## 一、全库扫描结果（事实）

判据：模型有 `createdAt` 但**没有** `updatedAt` → 追加型（只写不改），逐一核对。

| 表 | 当前行数 | 性质 | 处置 |
|---|---|---|---|
| `ExternalCallLog` | 28566 | 外部调用元数据（服务名/耗时/成败，**无正文与凭据**） | ✅ **已有保留期**（默认 365 天，0=不清理；cron 每周日清理） |
| `AuditLog` | 1073 | 审计留痕 | ⚠️ **必须全留**（触发器禁删），**归档路径缺失** → 见 §三 |

| `MatterLink` / `WorkResponsibility` / `MatterHandover` / `IntakeHandover` / `ExecutionTermination` / `IntakeUrgentItem` | 0 | 关系与责任留痕 | 全留：责任追溯依据 |

**结论**：真正需要保留期的只有 `ExternalCallLog`（已做）与 `AuditLog`（政策禁删、实现在缺）。

## 二、为什么其他表不做保留期

不是「懒得做」，而是**删了会失去可举证性**：

- **财务类**：核销、冲正、结算、发票调整——律师行业对账期常跨年，删一行就少一条证据链。
- **责任类**：交接、终止、紧急项——出问题时第一个被问的就是「谁在什么时候改的」。
- **证据类**：材料附件、门户授权、WebAuthn 凭证——授权记录被删，等于无法证明「他同意过」。

这些表的增长量级由**业务事件数**决定（一个所一年几千条），不是由技术调用频次决定。
按每行 1KB 估算，一年十万行约 100MB，不构成压力。

## 三、`AuditLog` 的缺口：有政策、无实现

**事实**：
- 数据库触发器 `audit_log_no_delete` 禁止任何删除，报错文案为
  「**审计日志只能归档处置，不可由业务代码删除**」；
- 但**归档处置并不存在**（无归档表、无归档脚本、无分区）。

**因此审计表会无限增长**。按当前测试期 400–600 行/天估算，一年约 15–22 万行、约 150–200MB。
短期无碍，长期需处置。

### 三个方案（含代价，供决策）

| 方案 | 做法 | 代价与风险 | 建议 |
|---|---|---|---|
| A. 分区表 | `AuditLog` 改 PostgreSQL 声明式分区（按月），老分区 `DETACH` 后归档 | **需重建表结构**（高风险迁移，须评审 + 停机窗口）；触发器需按分区重建 | 数据量再涨一个量级后做，**是正解** |
| B. 归档表 + 受控删除 | 建 `AuditLogArchive`，复制后删原行 | 与触发器政策冲突：要么改触发器（削弱保护），要么留"后门"路径 | 不推荐 |
| C. 仅导出（现状） | 用既有 `/api/audit/export` 定期导出到外部存储 | 不解决库内增长，但**保证证据可带走**（换库/迁移不丢） | **当前采用**，零风险 |

### 当前可用的导出能力（既有，无需新写）

```
GET /api/audit/export?format=json        # 也支持 cef / syslog（SIEM 对接）
    &from=2026-01-01T00:00:00Z&to=2026-06-30T00:00:00Z
```

- 需系统管理员或合伙人；
- 单次上限 **5000 行**，返回 `truncated` 标志 → 超限要**按时间分段**导出；
- 每条带 `integrityHash`，可校验审计链完整性；
- 导出动作本身写审计 `AUDIT_EXPORT`——**导出不是不可追溯的数据出口**。

实测（2026-11-22）：`format=json` → 200，`count: 1073, truncated: false`；
带 `from/to` 分段 → 200，43KB。

## 四、维护约定

- 新增「追加型」表时，必须在本文件里登记性质与处置（有新表不登记 = 文档失效）。
- 保留期类表统一走 `server/settings/retention.ts` 的可配置 + cron 模式，不要各写一套。
- 任何删除历史数据的改动，先问一句：**删了之后，还能不能举证？**
