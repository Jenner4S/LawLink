## 二、从字段反推的业务模型（推断，注明依据）

### 1. 这是一门「买流量 + 私域转化」的生意

依据：**渠道=本地生活、二级渠道=大众点评**，加 **团购金额** 字段。

→ 律所在大众点评/抖音本地生活投**团购券**（如 9.9 元咨询券、99 元面谈券）获客。团购金额是**投放成本侧的线索**（或客户实付券款）。
→ 这解释了为什么「到店」是核心环节：**团购券必须到店核销**，不到店等于钱白花。

### 2. 真正的 KPI 是「加微率」与「到店率」，不是"线索数"

依据：**添加微信是勾选框**（不是备注），**到店来访是状态单选**（未曾来访）。

→ 平台线索 → 电话/在线咨询（**对接方式**）→ 加微信（私域沉淀）→ 邀约到店 → 律师谈案 → 成交。
→ 每一步都是**可计数的转化**，所以做成单选/勾选而不是自由文本。

### 3. 多人分角色接力，并且要按角色算钱

依据：**对接人 → 二次对接人 → 对接律师**（三条人字段），以及 **案源人 / 邀约人 / 面谈签约人**（C 组三角色）。

→ 一次成交的功劳要拆给三个人：谁带来的（案源）、谁约来的（邀约）、谁谈成的（面签）。
→ 这三个人**不是同一个字段的三种叫法**，是**三笔绩效**。

### 4. 财务口径比"合同额 + 实收"更细

依据：合同金额 / 到账金额 / 到账日期 / **风代比例** / **风代金额** / **退款及无法收取费用差额** / 应收款 / 委托状态。

→ 存在**风险代理**（按比例后收），所以合同额不等于可收金额；
→ 存在**退款**与**确实收不回来**（坏账），两者被合在一列——客户把"钱少了"当一件事看，但成因不同。

### 5. 反复咨询是常态，所以专门做了「联系方式-是否重复」

依据：**联系方式-是否重复** 是独立字段（图 1 高亮），而非靠人眼判断。

→ 同一客户会多次来电/多平台来单。不识别就会：两个销售撞单、老客户被当新客户重新教育、投放重复计费。

### 6. 一个客户可能多次委托，所以有「委托次数」+「父记录字段」

依据：**委托次数**（数字）、**关联/父记录字段**。

→ 客户第 2 次委托时，新记录挂到旧记录下，形成父子关系，并把次数累加。

## 三、LawLink 现状对照（事实，来自当前代码）

| 客户的字段/能力 | LawLink 现状 | 结论 |
|---|---|---|
| 客户名称 / 联系方式 | `Lead.name` / `Lead.phone` / `Lead.wechat` | ✅ 有 |
| 客户职业或行业信息 | `Client.industry` | 🟡 部分（有行业，无"职业"） |
| 渠道（一级） | `Lead.source` 枚举（转介绍/网络/地推/合作/广告/其他） | 🟡 部分（枚举固定，不等于"本地生活"这类投放平台） |
| **二级渠道** | 只有 `Lead.sourceDetail` 自由文本 | ❌ 缺（无法按平台聚合 ROI） |
| **团购金额** | 无 | ❌ 缺 |
| **添加微信** | `wechat` 字段有值≈加了微，但没有显式标记与口径 | 🟡 半有（可推出，不可统计"加微率"） |
| 对接日期 / 对接方式 / 对接人 | `LeadActivity(happenedAt, channel, createdById)` | ✅ 有（时间线正好是这三项） |
| 当次跟进详情 | `LeadActivity.note` | ✅ 有 |
| **联系方式-是否重复** | 无任何手机号查重（客户档案只按证件盲索引比对） | ❌ 缺 |
| 到店来访（三态） | `Lead.stage` 的 `VISITED` + `visitedAt` | 🟡 半有（只有"到店了"，没有"**爽约**"，也没有"未曾来访"作为显式态） |
| 到店日期 | `Lead.visitedAt` | ✅ 有 |
| 案件类型 | `Lead.category`（MatterCategory 枚举） | ✅ 有 |
| **二次对接人** | 无（只有 `Lead.ownerId` 一个负责人） | ❌ 缺 |
| **对接律师 / 对接律师状态** | 无 | ❌ 缺 |
| 成交状态 | `Lead.stage = CONSULTED/CONVERTED/LOST` | 🟡 半有（无"待成交/无法成交"的语义分层） |
| **委托次数** | 无（客户多案天然存在，但没有计数口径） | ❌ 缺 |
| 案源人 / 邀约人 / 面谈签约人 | `CommissionPlan(matterId, userId, percent, label)` 可表达任意角色 | 🟡 半有（**机制有，语义没规范**，界面上没人引导按三角色填） |
| 承办律师 | `Matter.ownerId` | ✅ 有 |
| 委托类别 / 案件类型 / 对方名称 / 对方身份 / 签约主体 | `Matter.category` / `Party` / `Billing` 相关 | ✅ 有（模型比宽表更规范） |
| 合同金额 | `Billing`（一案一签 + 补充协议） | ✅ 有（比单列更强：支持追加/调减） |
| 到账金额 / 到账日期 | `FeeEntry`（两步确认）+ `Payment` | ✅ 有（且有确认留痕，比宽表强） |
| **风代比例 / 风代金额** | 只有 `contingencyTerms` **自由文本** | ❌ 缺（不可计算、不可统计） |
| **退款** | `Payment.refundedAmount` | ✅ 有 |
| **无法收取费用差额（坏账）** | 只有 `writeOffRate` 统计口径，无坏账登记实体 | ❌ 缺 |
| 应收款 | `Allocation` 核销后派生 | ✅ 有（口径比宽表更严） |
| 关联 / 父记录 | 无（多案各自独立，无父子链接） | ❌ 缺 |
| 可配置列 / 筛选 / 分组 / 排序 / 行高 | 固定列表 + 既有 `custom-fields` 模块 | 🟡 部分（**不建议追通用多维表格**，见 §六） |

**结论（事实层面）**：LawLink 在**委托之后**的模型比客户宽表强（合同/实收两步确认/核销/审批链）；
差距全部集中在**委托之前**（投放渠道结构化、加微与到店口径、重复咨询识别）和**钱的三处细节**（风代、坏账、三角色分账）。

## 四、差距清单与实施方案（按价值排序）

### P0 · 不做就替代不了他现在那张表

#### P0-1 渠道两级 + 投放金额（对应：渠道 / 二级渠道 / 团购金额）

**为什么是 P0**：他现在靠"渠道 + 二级渠道"决定**钱往哪投**。LawLink 现在只有固定枚举 + 一段自由文本，导不出"大众点评这个月来 40 条、成交 3 单"。

**方案**（可配置 + 有主张的默认，遵循 AGENTS §五之二）：
- 新增 `LeadChannel` 模型：`id / name / parentId（自引用两级）/ kind（PAID/ORGANIC/PARTNER）/ active / sort`。
- `Lead.source` 枚举**保留**（历史数据与统计兼容），新增 `channelId` 关联；默认给常用渠道预置种子数据（本地生活/大众点评、抖音本地生活、转介绍、官网、公众号、老客户）。
- `Lead.voucherAmount`（团购/券金额，Decimal 可空）——用于算「投放成本 / 成交」。
- 管理后台可增删渠道（两级），线索表单先选一级、联动二级。
- **验收**：按渠道/二级渠道聚合线索数、到店数、成交数、投放金额 ROI；停用渠道不影响历史数据。

#### P0-2 手机号查重（对应：联系方式-是否重复）

**为什么是 P0**：撞单是最直接的内部冲突，他现在专门设了字段。

**方案**：
- 线索创建/编辑时按**归一化手机号**（去空格、去 `+86`、去横线）查：`Lead.phone`、`Client` 关联联系人、`Intake.contactPhone`。
- 命中 → **不阻断**，返回命中摘要（哪个客户/哪条线索/谁在跟/最近一次跟进时间），由人判断是否同一人（同一号码可能是家人代接）。
- 线索列表显示「重复」徽标；`Lead.duplicateOfId` 记录人工确认的重复关系（可空）。
- **验收**：同号第二次登记必出提示；不同号不误报；确认重复后两条线索互相可见。

#### P0-3 到店三态 + 爽约（对应：到店来访 = 未曾来访）

**为什么是 P0**：「约了没来」和「没约」是完全不同的管理问题。现在 `stage=INVITED` 无法区分"还没到约定的时间"和"过了时间没来"。

**方案**：
- 新增 `LeadStage.NO_SHOW`（爽约）或在 `Lead` 加 `visitOutcome`（PENDING/ARRIVED/NO_SHOW）。
- 选择 `visitOutcome` 而非新 stage：因为爽约后仍可再约，`stage` 会回退，语义会乱；到店结果是**事件属性**，不是阶段。
- 爽约 → 自动进入我的邀约提醒链（已实现：1/3/7 天追问），并在漏斗里单列「爽约率」。
- **验收**：爽约可不改阶段；漏斗新增爽约率；爽约线索仍能再次邀约。

#### P0-4 风险代理结构化（对应：风代比例 / 风代金额）

**为什么是 P0**：他现在按比例看风险代理金额。LawLink 只有一段自由文本，**算不出、统计不了**。

**方案**：
- `Billing` 增加 `contingencyPercent Decimal?`（0–100）；`contingencyTerms` 保留为补充说明。
- 风代金额**不落库**，按「实收 × 比例」派生（避免与实收口径打架）——但要明确：**风代的计提基数是回款，不是合同额**。
- 财务页在风代案件上显示「按当前实收计提 X 元（比例 Y%）」。
- **验收**：风代案件可按比例算出计提额；非风代案件不显示该块；比例变更留审计。

#### P0-5 坏账登记（对应：退款及无法收取费用差额）

**为什么是 P0**：他把"退款"和"收不回来"合在一列，说明两件事都在发生。LawLink 只有退款，没有坏账，**应收会永远挂着**。

**方案**：
- 新增 `ReceivableWriteOff` 模型：`matterId / billingId? / amount / reason(枚举：客户失联/无力支付/减免/争议) / note / approvedById / createdAt`。
- 写坏账必须走审批（金额影响收入与提成），审批后从"应收"里剔除并在报表单列「本期坏账」。
- **验收**：坏账需审批才生效；生效后应收下降且可追溯；报表坏账率 = 坏账/应收。

### P1 · 明显提升，但不阻塞替代

#### P1-1 三角色分账规范化（案源人 / 邀约人 / 面谈签约人）
`CommissionPlan` 机制已有（userId + percent + label）。缺的是**语义**：
- 预置 label 常量：`REFERRER`（案源）/ `INVITER`（邀约）/ `CLOSER`（面签），允许自定义。
- 分成方案弹窗改为「按角色添加」三行式，percent 合计≠100% 时提示（不阻断，允许特殊约定）。
- 线索转收案时，把 `Lead.ownerId` 与 `Lead` 的邀约动作记录人**预填**为邀请人建议值（仅建议，需人确认）。
- **验收**：能按角色查分账；同一人可兼多角色；合计不为 100% 有提示。

#### P1-2 对接律师 + 对接律师状态
- `Lead.assigneeLawyerId`（对接律师）+ `assigneeStatus`（未分配/已分配/已接/拒接/忙）。
- 拒接需填理由（与现有 `markLeadLost` 同风格）。
- **验收**：可看「待分配律师」队列；拒接有理由留痕。

#### P1-3 二次对接人
- `Lead.secondOwnerId`（二次对接人）+ `handoverAt`。
- **验收**：线索可两人跟；时间线显示谁在什么时候交接。

#### P1-4 委托次数
- 派生指标，不落库：`count(Matter where primaryClientId = client)`。
- 客户详情页显示「第 N 次委托」，列表可按次数排序。
- **验收**：同一客户多案时计数正确；软删案件不计。

### P2 · 有则更好

- **父子记录（二次委托关联）**：`Matter.parentMatterId`（自引用，可空），用于把"同一客户的续案/二案"串起来。需 Schema 迁移。
- **客户职业**：`Client.occupation`（`industry` 已有）。
- **成交状态分层**：`待成交/无法成交` 的细分原因（现在是 `lostReason` 自由文本）。

### 明确不追（有理由，写清楚避免以后反复讨论）

**不追通用多维表格能力**（自定义视图、行高、填色、公式列、冻结列配置）。
理由：那是产品形态差异。客户用宽表是因为**没有领域模型可用**；LawLink 的价值恰在模型（审批链、两步确认、核销、权限墙）。追平表格灵活性等于放弃模型优势，且工作量为重写。
**替代方案**：既有 `custom-fields` 模块已支持案件自定义字段；若客户需要"列表显示哪些列"，做**列显隐配置**（低成本）即可，不做公式列。

## 五、分阶段计划与排期

| 阶段 | 内容 | 依赖 | 预估 |
|---|---|---|---|
| **A** | P0-2 手机号查重、P0-3 爽约态、P1-4 委托次数 | 无迁移（P0-2 用现有字段） | 1 批 |
| **B** | P0-1 渠道两级 + 券金额（1 迁移 + 管理页 + 联动表单） | 需迁移 + 种子 | 1–2 批 |
| **C** | P0-4 风代比例、P0-5 坏账登记（1 迁移 + 审批链复用） | 需迁移 + 审批 | 2 批 |
| **D** | P1-1 三角色分账规范化、P1-2/P1-3 对接人与二次对接人 | 无迁移（P1-1） | 1 批 |
| **E** | P2 父子记录、客户职业、成交状态细分 | 需迁移 | 视反馈 |

**A 段为什么排第一**：三件事都不改 Schema（除非查重要落 `duplicateOfId`），却直接对应他现在**每行都在填**的字段，改完立刻能对比新旧系统。

## 六、风险与取舍

| 风险 | 处置 |
|---|---|
| 渠道做成可配置后，历史枚举与新渠道并存，统计算重 | `Lead.source` 保留为"来源大类"，`channelId` 为具体渠道；聚合优先用 `channelId`，为空时回退 `source`。口径写进代码注释与文档 |
| 手机号查重误报（家人代接、公司总机） | **只提示不阻断**，且提供"确认不同人"标记，避免把真实新客户挡在门外 |
| 坏账审批增加摩擦 | 金额阈值以下可单人确认（可配置），超阈值走审批 |
